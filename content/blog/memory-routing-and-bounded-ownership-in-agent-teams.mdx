I run a few agents at once. One handles content, one handles code, one handles routine ops. They each have their own preferences, their own tone rules, their own memory of what's already been done.

When I let them share too much, the work gets worse, not better. The site builder picks up a phrasing rule that belonged to the email pipeline. The growth agent quotes a stale assumption from a customer thread. Nothing's catastrophically wrong, but the lanes blur, and "more context" stops feeling like coordination.

In [Operator Control for Agentic Systems](/blog/operator-control-for-agentic-systems/), I argued that production-worthy agent systems need visible work, clear ownership, approval points, and intervention paths. The real product layer is operator trust.

That gets harder when more agents are involved. A single agent with too much hidden context is already tricky to trust, and a group of agents sharing everything with everyone makes it worse. More context starts to feel like coordination, but in practice it produces blurry ownership, stale assumptions, and bugs that are hard to trace because the failure came from unrelated context pulled in silently rather than the prompt or tool.

The better pattern is bounded ownership: memory has an owner, work has an owner, routes are explicit, and handoffs preserve operator visibility instead of dumping every context into every agent.

## The shared-context trap

The tempting move in a multi-agent system is to make every agent aware of everything. Give the builder agent all the product history, give the growth agent all the engineering context, give the support agent every customer note, give the ops agent every workflow and prior decision. At first, this feels powerful. Nobody is missing context, every agent can answer more questions, the system feels less brittle because the context window is full.

That fullness has a cost. When every agent has access to everything, responsibility gets blurry. An agent starts using stale information from another lane. A specialized task gets influenced by irrelevant background detail. A memory that should belong to one product or workflow quietly shapes another. Debugging gets harder because the failure might not be in the prompt, the tool, or the model. It might be in polluted context, and polluted context doesn't surface as an error.

More context doesn't give you better coordination on its own. Without boundaries around what each agent reads and writes, extra context mostly adds noise.

## Context is not memory

One distinction matters a lot here: context is not memory.

Context is what the model sees during a single run. It's temporary, bounded, and shaped by whatever the system chooses to include this turn. When the run ends, the context goes with it.

Memory is what the system writes down for later. It lives in files, scoped stores, or workspaces the system controls, and it's recalled through explicit tools rather than pulled in by ambient gravity. Useful memory has an owner.

That distinction matters because memory shouldn't turn into a shared dumping ground. Before persisting anything, the system needs clear answers on who owns the record, which agents can read it, whether it belongs only to the current task, whether an operator should approve the write, and when it gets updated or retired. Without a clear owner, persisted notes quietly drift into ambient influence that's tough to inspect or debug later.

## Product-owned memory

I treat memory as product-owned by default. Depending on what it governs, a durable note belongs to a specific product, workspace, agent, or workflow, and plenty of intermediate context should stay temporary and never be persisted at all.

A site builder agent needs durable facts about publishing rules, voice, content structure, and approval boundaries. A growth agent needs positioning patterns, distribution preferences, and audience notes. A control-plane agent needs implementation facts, docs paths, and operational caveats.

Keeping those stores separate isn't about secrecy. It's about relevance and reviewability. If a stored note affects public writing, I want to know where it came from and which lane owns it. If it affects tool permissions or operational behavior, that boundary matters even more.

## Specialist agents need lanes

The same principle applies to agents themselves. A growth agent, a builder agent, a support agent, and an ops agent shouldn't be the same general assistant wearing different labels. Each one needs a lane.

That lane should include:

- what kind of work it owns
- what memory it can rely on
- what tools it should use
- what claims it's allowed to make
- when it should escalate
- when it should hand work to someone else
- what it shouldn't touch

I like the "desk" metaphor for this. A desk has a job. Work comes in. The desk either handles it, routes it, or escalates it. It doesn't pretend to own everything. That makes the system more legible for the operator. If a content draft is weak, I know which lane produced it. If a product claim needs verification, I know which lane should review it. If a workflow is blocked, I can tell whether it's a routing issue, an ownership issue, or a missing approval.

Giving agents specialist names only helps once each desk actually owns its files, tools, and escalation rules.

## Routing is where ownership becomes real

Routing is where the system actually assigns ownership.

A practical routing layer decides five things up front: what kind of task came in, which desk owns it, what context gets included or left behind, whether it's a new run or a handoff, and when an ambiguous route needs an operator decision instead of a guess.

In a system built this way, agents have separate workspaces, state, sessions, and bindings. Inbound work gets routed by rules. Cross-agent memory access is explicit, not automatic. That matters because it keeps coordination from turning into accidental context sharing. Routing should make ownership clearer, not hide ownership behind a smoother interface. If work moves from one agent to another, the operator should be able to understand why.

## Handoffs shouldn't be context dumps

A sloppy handoff dumps the entire transcript into the next agent and hopes for the best. A structured handoff names what's being transferred, why another agent is needed, what artifact already exists, what context is included or intentionally excluded, what output is expected, and which approval boundaries still apply.

Handoffs are where multi-agent workflows usually lose coherence. Make them too thin and the receiving agent wastes turns reconstructing prior work. Make them too broad and it inherits noise from another lane. Hide them completely and you can't tell who owns the next step.

Writing down the handoff contract keeps the transition inspectable so you don't have to guess whether the second agent understood the first agent's intent or still respects the original approval gate.

## The memory boundary is also a safety boundary

Memory scoping affects safety as much as output quality.

When an agent saves a bad assumption, that mistake keeps showing up in future runs. When a private detail leaks across lanes, it can end up shaping public output where it doesn't belong. And when a one-off instruction gets stored as durable memory, the system starts treating a passing preference like a permanent policy.

Low-risk, narrowly scoped updates can happen routinely, while higher-impact durable memory changes should be proposed, reviewed, and approved before they stick.

This connects directly to operator control. The operator doesn't need to approve every token. The operator should have visibility and control around durable context that changes how the system behaves later.

## The operating model

The pattern this points to is simple:

- scoped agents instead of one universal assistant
- memory written into inspectable workspace files instead of hidden model state
- explicit memory access instead of automatic cross-agent recall
- routing rules that decide who owns inbound work
- task and workflow layers that make work easier to inspect
- operator-visible handoffs when ownership changes
- approval points around durable memory, external action, and risky changes

I'm applying this layout in my OpenClaw setup and other multi-agent projects, though the pattern itself isn't tied to any specific platform. The aim is to get the right agent working on the right task with only the context it needs.

If you're setting up a multi-agent workflow, settle three things before you start feeding agents more context: who owns durable memory, which lane owns each type of task, and what a valid handoff looks like. Skip those decisions and you usually end up with one shared context blob wearing four different names.
